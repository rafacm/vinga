### Fixed

- **Two runs of the migration autogeneration command against one Postgres no longer break each other** (#585). `python -m vinga_server.db.migrations.autogen` made its throwaway database under one fixed name, `vinga_autogen_scratch`, and dropped it with `force` before and after the run, so a second run on the same instance terminated the first one's connections and dropped its database mid-use. It showed up as an intermittent `tests/unit/test_db_autogen.py` failure whenever two worktrees' test lanes shared the development instance. Each run now makes a database named `vinga_autogen_scratch_` plus a random suffix and drops only that one, with `force`, when it finishes. A run killed before it could clean up leaves its database behind and nothing removes it automatically, since a database a concurrent run is still using looks the same from outside: find leftovers by the `vinga_autogen_scratch_` prefix in `pg_database` and drop them by hand. The old fixed-name database, if a killed run of an earlier build left one, is not touched and can be dropped the same way.
