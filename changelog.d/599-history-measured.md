### Added

- **Every request an agent sends says what its history lost on the way out** (#599). `llm_round`, a recap's included, and `provider_failed` for an LLM request that failed after it was built, a context-length refusal included, gain `cleared_results` and `cleared_bytes`, how many earlier replies' tool results over 2 KiB the request sent as the cleared note and their original sizes summed in UTF-8 bytes; `cleared_largest`, the largest of them; `cleared_tools`, how many per tool, keyed `builtin.<name>`, `mcp.<entry>`, `device` or `unknown` from the origin the call was made with, so a result from an MCP entry since removed is still keyed by that entry; and `degraded_calls`, the earlier calls sent as the quoted record because the request no longer offers their tool. The counts are zero and the other two absent when nothing was lost, and no other stage's failure carries any of them. The `llm` span carries them as `vinga.llm.history.cleared.count`, `vinga.llm.history.cleared.bytes`, `vinga.llm.history.cleared.largest`, `vinga.llm.history.cleared.tools.<key>` and `vinga.llm.history.degraded.count`. `llm_round.turns` counts the kept tool turns as well, so a series crossing this change steps up.
- **A tool call says whether it asked again for a cleared result** (#599). Every `tool_call` gains `refetch`, true when the call repeats, by tool and by arguments compared with their keys sorted, an earlier reply's call whose result its request carried cleared; grouped by `conversation` it counts re-fetches per conversation, across sessions. The tool span carries it as `vinga.tool.refetch`. A call whose arguments were not a JSON object is never a re-fetch, and a handover, a new conversation or a resume emits no `tool_call`, so a repeated move is not counted. Like every field above it is a count, a size, a flag or a naming-policy key: no result, argument or far-side tool name reaches it.
