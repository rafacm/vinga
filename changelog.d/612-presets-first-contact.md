### Changed

- **The presets and Getting Started configure engines, and vinga is the first agent** (#612). `examples/presets/local-stack.yaml`, `examples/presets/cloud-stack.yaml` and Getting Started's step 3 document now write providers and `agent_defaults` only, with no agent and no default agent, so the first agent a new deployment has is vinga, the built-in one: a board claimed by its code with no agent named is bound to it, and step 5 says what to ask it. The MAC binding the presets quote, and the recipes on `docs/reference/cli.md` read from them, name vinga.
- **The local default model is Gemma 4 e4b** (#612). The local preset, the `openai_compatible` example, Getting Started and the model guide name `gemma4:e4b` in place of `qwen3:8b` and `llama3.1:8b`, with `reasoning_effort: none` so it does not stream its thinking before every reply. On a Raspberry Pi 5 the model guide and Getting Started now say plainly that the first turn after the model loads does not fit: a first request of about 2,000 tokens took 107.6 s to its first byte, while the first-token watchdog gives the turn up after its retry, about 20 s in with the default, and no setting waits past the fixed 30 s transport bound, so the turn ends in the fallback phrase.

  Upgrade: nothing to run. An existing deployment is untouched: importing a preset is additive, so an `assistant` agent, a default agent and the bindings already stored stay as they are, and a board bound to `assistant` keeps reaching it, with vinga beside it. To move an existing local deployment to the new model, `ollama pull gemma4:e4b`, write it and `reasoning_effort: none` into the LLM entry its agents use, and apply, as [Choosing the model an agent thinks with](docs/run/llm.md#ollama) shows; importing the new preset over an existing deployment replaces the entries and `agent_defaults` it names.
