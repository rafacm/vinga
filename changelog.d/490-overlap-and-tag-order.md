### Fixed

- **A merge no longer loses its image to the merge behind it** (#490). The workflow held one running run and one pending run per branch, and a third arrival replaced the pending one whatever the cancellation setting said, so a commit merged during a busy hour could be dropped before a single job of its run had started. It has happened: the run for `d6d76dd1` sat pending for fourteen minutes on 2026-09-11, started no job at all, and was terminated one second after the next push's run was created, which is why `main` carries a commit with no published image and no red run to say so. Pull requests keep the group that cancels a run nobody will read; every other event now gets a group of its own, so nothing queues and nothing is displaced. Two runs can therefore publish at once, and the publish job now reads which commit the image a moving tag points at was built from and leaves the tag alone when that commit is the newer one, so `latest` and `slim` are not moved backwards by a slower run. Reading that commit is an ancestry question, so the publish job now checks out the repository's history, which the entry above says it does not; that was true when it was written and this is the change that makes it false. That check is a read before a write rather than a lock: it keeps the tag from going backwards, not from being briefly a commit behind, and the tags to deploy from are the immutable ones either way.
