### Added

- **A guide a coding agent can be pointed at** (#611). `docs/run/with-a-coding-agent.md` is written for a coding agent, such as Claude Code or Codex, that a person asks to install, configure or check a vinga deployment for them. It reads the documentation at the server's revision (a published image's twelve characters on GitHub, a checkout's `git describe` from the checkout, and a stated action for an `unknown` build, a dirty tree and a deployment older than the page, never falling back to `main`), fetches files and installs a workstation client at that same revision, and learns the domain model before asking anything. It keeps three rules, each with what goes wrong without it: facts from the installed client's `--help`, state from `vinga info`, `list`, `show` and `diff`, and secrets typed by the person, with the deployment's secrets, a vendor's key and the board's NVS named as steps the person runs. It follows Getting Started and then the task guides' index, asks a short interview that shows what is stored, changes only what was asked and diffs before writing and again before applying, and proves a reply comes back with `vinga simulator run` while `vinga events tail --follow`, started first, shows `replied` or the failure events. The task guides' index lists it first, the Run door and Getting Started link it, and `AGENTS.md` sends a coding agent asked to run a deployment there instead. Getting Started's `.env` block now builds the file in a new one only its owner can read, with `openssl` writing the two secrets straight into it, and moves it into place only once it is whole, so a rerun over an older, wider-open `.env` replaces it rather than writing secrets into it. The security guide's master key is now generated by the server image's own Python, which carries `cryptography` where a host need not, and reaches the env file only when generating it succeeded.
