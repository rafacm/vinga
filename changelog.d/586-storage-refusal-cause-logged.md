### Fixed

- **A storage failure the API answers with a 500 now names what failed in the server's log** (#586). A memory write or a conversation erasure the database refused answered "The details are in the server's log", and the one line the request logged, `api_storage_error`, named only `StorageError`, the class of the refusal rather than of the failure under it. It now names the class of the exception the database layer raised, such as `OperationalError` or `ProgrammingError`, and so does the same line for a configuration store failure, whose response already named that class while its log line did not, and for the reload and configuration diff routes, whose refusals dropped it on the way. Only the class name is logged, and only when it is an identifier; a class whose name is not one leaves the line naming `StorageError` as before. Nothing else of the failure is logged, and no response body changes. A consumer matching `api_storage_error` on `(StorageError)` for these failures needs the cause's class instead; a stored row that will not read as configuration still logs `StoredConfigUnreadableError`. The committed OpenAPI document's 500 descriptions, which said "The details are in the server's log", now say what the log holds: the class of what failed, and nothing else of it.
