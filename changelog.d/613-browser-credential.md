### Added

- **A browser can present itself as a device, and the server gives its client a home** (#613). The websocket edge now also reads a device's identity and token from `Sec-WebSocket-Protocol` values (`vinga.device.v1`, `vinga.mac.<12 hex>`, `vinga.client.<uuid>` and, when the deployment issues tokens, `vinga.token.<token>`) whenever none of a board's `Authorization`, `Device-Id` and `Client-Id` headers is present, checks the token exactly as it checks a board's, and accepts selecting `vinga.device.v1`, never the value that carries the token; a board's handshake is unchanged. With onboarding on, the server serves a placeholder page at `/try/` (no key, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and a Content-Security-Policy that keeps its scripts and connections on its own origin) and its modules at `/try/static/<version>/<file>`, immutable, from a fixed allowlist, where the version is a digest of the files' bytes. `POST /x/<key>/try-identity` on the onboarding path mints a browser's identity, a random locally administered MAC and a client id derived from it, and refuses while a default agent is set, since that agent would admit the browser without pairing. The browser client itself is not built yet; the page only proves its routes. `server.ota_path` now also refuses `/try/` and anything under it, where the page is served.

  Upgrade: a deployment whose `server.ota_path` is `/try/` or under it is refused at boot; move the OTA endpoint elsewhere, for example `/xiaozhi/ota/`, and write the new URL into each board that used it.
