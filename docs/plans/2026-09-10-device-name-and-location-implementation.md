# Device name and location: implementation

Companion to
[`2026-09-10-device-name-and-location.md`](2026-09-10-device-name-and-location.md),
one section per milestone, appended in the same change that ticks the
milestone checklist. It records deviations from the plan, resolutions of
the plan's open questions, and discoveries.

## M1: the device record

The whole of the domain half: the schema, the migration, the fold in its
proved-equal renderings, the repository's minting and its folded-name
refusal, the widened value-shape union, and every device ingress changed
by name. Nothing in the runtime moved, which is M2's.

### What was built

- **The schema.** `domain.devices` gains `id` (the primary key, an
  application-minted uuid hex), `name` (`Text NOT NULL`) and `location`
  (`Text`, nullable). `mac` is demoted from primary key to
  `NOT NULL UNIQUE` and stays selectable. No `Identity()` row id, per the
  issue's decision: these rows are read whole and assembled in Python, so
  a cursor id would be a column with no reader. A functional unique index
  `uq_devices_folded_name` sits over the folded name.
- **`3003_device_record`**, hand-written rather than autogenerated,
  because autogenerate can write the column adds and the key move and
  cannot write the two backfills between them. It adds `id` nullable,
  mints one per row with `gen_random_uuid()` with the dashes taken out,
  sets it `NOT NULL`, moves the primary key from `mac` to `id` while
  adding `uq_devices_mac`, adds `name` nullable, backfills
  `'Device ' || mac`, sets it `NOT NULL`, creates the functional index,
  and adds `location`. The fold is a frozen literal, per the issue's
  decision.
- **The fold**, exactly as the plan defines it: lowercase by the simple
  case mapping, collapse internal runs of Unicode whitespace to one
  space, trim the ends. Two declared renderings,
  `models.fold_device_name` and `models.device_name_fold_sql`, plus the
  migration's frozen copy, proved equal against Postgres over one corpus
  in `tests/unit/test_device_name_fold.py`.
- **`DeviceRecord`**, in `config/models.py` beside the device's other
  facts, with `id`, `name` and `location` all optional and `agents`
  required. Absence means "the repository decides"; an explicit
  `location: null` means "nowhere in particular", told apart from absence
  through `model_fields_set`, the way `default_agent` already tells them
  apart.
- **`normalize_device_bindings`** absorbs the value-shape union and
  nothing else. A bare agent list is shorthand for a record naming only
  those agents. It does not mint.
- **The repository.** Every device write runs the same four phases every
  other write runs, through one private `_device_write`: staged into the
  candidate state the transaction read, checked once against it,
  persisted. `_stage_device` is where the id is decided, under the domain
  writer lock with the stored row in hand.
- **Five device verbs** on `ConfigStore`: `bind_device`, `claim_device`,
  `rename_device`, `relocate_device`, `clear_device_location`, all
  answering with the record the row now holds.
- **The CLI and the API**: `device rename`, `device relocate`,
  `device clear-location`, over `POST /devices/{mac}/rename`,
  `PUT /devices/{mac}/location` and its `DELETE`.
- **The documentation**: `config.example.yaml`, `docs/concepts.md`,
  three new glossary entries, `CHANGELOG.md`, and the three generated
  references through their own generators.

### The lookup path, pinned before and unchanged after

`tests/unit/test_live_binding_pin.py` was committed green **before** the
schema changed (commit `0bb0e0b5`) and is byte-unchanged after. It pins
two different kinds of promise: the exact SQL the two statements send,
captured off the psycopg cursor rather than read off the source so a
widened select cannot pass unnoticed, and the answers for a bound
device, a device with no row, a default agent standing behind one, and a
MAC spelled the other way.

The statements are unchanged:

```
SELECT domain.devices.agents
FROM domain.devices
WHERE domain.devices.mac = %(mac_1)s::VARCHAR
```

which is why `mac` kept `UNIQUE` rather than becoming an ordinary
column.

### How `apply` is proved idempotent

Three tests, in increasing order of what they are about:

- the same document applied twice reports `wrote` once and then never,
  and the id after the second apply is the id the first one minted;
- an exported document applied back onto the store it came from writes
  nothing, with the whole record compared before and after;
- a document leaving `name` and `location` out keeps the stored ones
  rather than resetting them.

The plan's ninth review finding is why id preservation is asserted by
reading the row rather than by reading a diff: `config_diff` represents
devices as `LiveKind(applies=CHECK_IN)` and performs no device
comparison, so it cannot report a changed record. The differ contract
was not expanded.

### Every device ingress, found and changed

The plan's second finding said the ingresses do not inherit writing from
the parser. Each was changed explicitly, and each is driven by name in
`tests/unit/test_device_record.py`:

| Ingress | What changed |
| --- | --- |
| `bind_device` | Routes through `_stage_device`; creates a record, mints an id, takes the `Device <mac>` default name |
| `claim_device` (the pending claim) | The same, with its two conditions unchanged |
| `apply` / `import` | `_change` builds a full `_DeviceBinding` from the record or the shorthand; `_stage_device` mints or adopts |
| The API writes | `PUT /devices/{mac}` and `POST /devices/pending/{code}` inherit the repository's minting; three new routes for the record's other fields |
| Stored-row loading | `_device` reads four columns into the record shape; `_read_domain` assembles `DeviceRecord`s |
| `_stage_rename` (the agent rename) | Rewrites the binding through `model_copy`, leaving id, name and location alone |
| `read_live_binding` | Reads the record's `agents` and nothing else; its SQL is unchanged |
| `DeviceBindings.names_for` | Reads `record.agents` from the served snapshot rather than the section value |

### Deviations from the plan

Four, each with its reason.

1. **`device location set` and `device location clear` are spelled
   `device relocate` and `device clear-location`.** The plan's milestone
   text enumerated the acts and also held the grammar to
   `docs/architecture/cli-guide.md`, and the guide decides the spelling:
   `/devices/{mac}/location` is a trailing segment with no identity after
   it, which the guide calls an attribute of its parent rather than a
   sub-noun, and it names `agent prompt show kids` as the constructed
   counterexample for exactly this shape. An attribute in the verb slot
   reads as a possessive, and `preview` is the merged precedent for
   giving such an act a verb of its own.
2. **A document that swaps two device names is refused rather than
   applied.** The plan asks for the folded-name check against the
   finished candidate state, and it is; what the plan did not anticipate
   is that a unique INDEX is checked statement by statement rather than
   at commit, and a functional index cannot be a deferrable constraint in
   Postgres because constraints cannot be written over expressions. So a
   document whose end state is fine but whose intermediate state is not
   would have depended on the order `_persist` happened to write two rows
   in. `DEVICE_NAME_IN_FLIGHT` refuses it with a sentence naming the
   remedy (do it in two steps) rather than letting the index answer with
   the generic sanitized database failure and a 500. Its test asserts
   both the refusal and that the two-step path works.
3. **A written `id` that disagrees with the stored one is refused rather
   than ignored.** The plan says a stored id wins over an absent one and
   is silent on a written one that disagrees. An id a write could replace
   would not be an identity, so `DEVICE_ID_FIXED` says so rather than
   letting it quietly not happen. A written id on a MAC with no row is
   adopted, which is what lets an exported document restore a deployment
   onto an empty database with the identities it had, and one id given to
   two devices is refused by `DEVICE_ID_TAKEN`.
4. **`vinga-server/examples/` gains no device fragment.** The plan's
   documentation footprint said "gains or updates the device example".
   There is none to update: `examples/` holds one fragment per
   fragment-written entity kind, and a device is written with verbs of
   its own rather than from a fragment, so a file there would be a
   document no command takes. The device's own shape is documented where
   the other two device facts are, in `config.example.yaml`'s header, in
   `docs/concepts.md` and in the generated domain reference.

### Discoveries

- **Python's whole-string `.lower()` cannot be the fold.** It applies
  the context-sensitive Greek final-sigma rule, so `ΑΣ` lowers to `ας`
  in Python and `ασ` in Postgres, and it applies the FULL lowercase
  mapping, so `İ` becomes two characters where a database's simple
  mapping gives one. Folding character by character removes the context,
  and U+0130 is named explicitly as the one expanding mapping. Both were
  measured against the running instance rather than reasoned about, and
  both are in the corpus.
- **`\s` is not portable into the index.** What a Postgres regular
  expression calls whitespace depends on the database's ctype, so a
  name's folded form would have been a property of how the instance was
  initialized. Both renderings spell the Unicode whitespace class out,
  and a test asserts the written set is exactly `str.isspace`'s.
- **The `ß` question answers itself once the fold is the case MAPPING.**
  `Straße` and `STRASSE` fold together under case FOLDING and apart
  under the mapping, so they are two devices. The corpus says so rather
  than leaving it to be discovered by an operator.
- **The respelling transcript could not be regenerated.** `expected()`
  applies a substitution table to the committed text, so capturing over
  it writes the post-substitution form and corrupts the differential.
  The device-record lines were hand-applied instead, and the minted id is
  substituted for a placeholder by `Recorded.rendered`, so the line stays
  pinned and only the digits do not.

### Review round

External review of PR #462 came back mergeable after fixes, with seven
findings. Each is answered by a commit of its own; the three that
changed behaviour rather than prose are recorded here.

**The SQL fold changed with the database locale.** Both renderings used
a bare `lower()`, which lowercases under the collation of its argument,
which is the database's default, which is whatever locale somebody ran
`initdb` in. Under a Turkish one `lower('I')` is `ı` where every other
locale answers `i`, so the repository would approve a name its own
Python fold called free and the index would then refuse the insert,
producing exactly the sanitized database failure `store.py` promises
cannot happen. The corpus proved agreement only for the collation the
test instance happens to have.

Both renderings now lowercase under `pg_c_utf8`, Postgres 17's built-in
collation provider at locale C.UTF-8, whose case mapping comes from the
Unicode character database rather than from the host's libc or ICU. It
applies the simple mapping and no context-sensitive rule, which is what
the Python rendering applies and why that one lowers character by
character. It sets this server's Postgres floor at 17, which every
deployment artifact here already pins. The corpus is driven a second
time with a foreign collation forced onto the value, over Turkish,
Azerbaijani, Lithuanian, C and US English, beside a control asserting
that on this very instance a bare `lower()` really does answer `ı`.

This is the third instance of one hazard, and naming it is the point:
Python's whole-string `.lower()`, `\s` in a Postgres regular expression
and now `lower()` itself are all resolved against something outside the
expression. What fixed each of them was the same move, which is to say
what is meant rather than to name a default.

**Both free-text fields bypassed the URL-credential refusal.** A device
name and a device location are stored exactly as written and read back
on every surface, which makes them the same hazard a provider's
`base_url` is, and neither was checked. The display stripped the
credential on the way out, so a name stored with one and re-applied from
an export would have come back as a different name and the apply would
have reported a write: the lossiness contradicted the idempotence this
milestone proved.

Refused at the repository boundary, on what a caller submitted and never
on what a row holds, which is the rule `_check_addressable` already
follows. `url_credential` is the detection, shared with the provider and
MCP walks; the sentence is the repository's own, because the remedy
those two give is to name an environment variable and a room is not an
address with a variable behind it.

**An empty location was a second way to say nowhere.** `location`
accepted any string, so a `PUT` and an applied document could both
persist `""` while the repository, the CLI and the generated API
contract all say a device is nowhere in particular when the field is
NULL, reached by a DELETE. Refused on the model, which is the one place
every ingress passes through, and on the FOLDED form rather than the
length, for the reason the name's rule is: a location of two no-break
spaces is not empty to a length check.

The remaining four were a documentation claim, two test weaknesses and
the PR number. The documentation one is the one most worth naming: six
pages and the descriptor the domain reference is generated from said
that per-device memory and recorded history already hang on the new id.
They do not. Memory is keyed by the MAC until M4 moves it, and history
deliberately stays under the MAC it was written with, because a dated
row says which board was connected at the time. The id is now described
as what it is in M1, a stable record identity, with the reason it exists
said as a reason rather than as a state.
