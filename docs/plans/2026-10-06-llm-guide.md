# A guide to choosing and configuring the LLM

Plan for [#364](https://github.com/rafacm/vinga/issues/364), the second
child of epic [#615](https://github.com/rafacm/vinga/issues/615). Its
companion is `docs/plans/2026-10-06-llm-guide-implementation.md`, one
section per milestone, appended in the same change that ticks it. It
builds on #609's task-guide directory and conventions
(`docs/plans/2026-10-05-three-doors-and-task-guides.md`, whose M3
records are the house style for a guide), and it is the page #609's
`providers.md` names as missing: the LLM stage's own guide.

**Local baseline:** not applicable. A guide to configuring an existing
stage changes no capability; the local recipe it leads with is the one
the baseline already names.

**Cheapest alternative:** a section added to `docs/run/providers.md`
instead of a page of its own. It would hold the same recipes and traps
in a page whose task is choosing between stages, not configuring one,
and it would leave #611's index and #610's Getting Started linking an
anchor inside another task. The issue's own shape, one guide, is the
smallest that gives the task a home; nothing in it is a number to
measure.

**Operator surface:** a procedure, `docs/run/llm.md`, listed in
`docs/run/README.md` and linked from Getting Started's step 0 and from
`providers.md`. No key, example, preset, readiness check or device
behavior changes (D1),
and nothing is asked of an operator on upgrade, so the changelog
fragment has no `Upgrade:` line.

**Attribution:** anthropic/claude-opus-5-5, thinking high; Claude Code 2.1.289; 2026-10-06.

## Decisions, restated

The issue's, as Step 0 confirmed them, with D1's amendment:

1. **The task shape is "point vinga at the model I actually want"**:
   worked recipes, each ending in the `vinga provider set llm ...` line
   and the `vinga agent set` or `vinga agent-defaults set` line that
   makes an agent use it.
2. **Four routes**: the default local runner and why; other local
   runners through `openai_compatible`; Anthropic; OpenAI and the
   OpenAI-compatible vendors.
3. **Four traps collected**: the container's view of `localhost`; the
   two credential paths, neither a `key=value` argument; `reach` is
   asserted for `openai_compatible` (formerly `egress`); tool calling is
   a requirement.
4. **It must not become a second source for field semantics**: it
   summarizes and links `docs/reference/domain-config.md`.
5. **Done when**: listed in the index under its class, reachable from
   Getting Started step 0, every recipe executed against a running
   deployment or saying plainly that it was not, link check and census
   green.

## Smaller decisions

**D1. The issue's default stands, and the guide states the
disagreement rather than resolving it.** The issue settles on
`qwen3:8b`, the model the local preset and the example name. Getting
Started moved to `llama3.1:8b` on 2026-09-05, on the 2026-09-03
walkthrough's measurements: over eight identical tool-using requests
`llama3.1:8b` made proper tool calls 8/8 with an integer argument 7/8,
while `qwen3:8b` is a reasoning model whose first content token trails
by 1.5 to 2.5 s, near the 10 s watchdog. Choosing one default is a
change to the issue's settled decision, which is Rafael's, not the
plan's. So the guide leads with the preset's `qwen3:8b` as the issue
says, states in the same section that Getting Started's step 0 installs
`llama3.1:8b` and why, and gives both against D2's criteria with the
measurements and their date, so a reader who did step 0 keeps the
model they have. The preset, the example and every other `qwen3` site
are left as they are. The open question (one default for the preset,
the example and Getting Started) is posted on #364 and named in the PR,
and whichever answer comes back is a one-line change in each of three
files.

**D2. The selection criteria are stated, so a reader substitutes with
judgement.** Three: the model makes real tool calls (an agent with MCP
or device tools needs them; a model without them looks like an agent
whose tools never fire, and a small model's argument types are
coerced only where lossless, #383's rule); its first token arrives well
inside `server.llm_first_token_timeout_s` once loaded (link the key);
it fits the machine's memory with the speech engines beside it. Each
criterion says how to check it (`ollama show <model>` for the tools
capability, `vinga events tail` for `llm_round` timings, `ollama ps`).

**D3. Cold load and the keep-alive pin are linked, not restated.**
Getting Started step 0 owns the pin procedure today; the guide says why
it matters for any local runner (the first-token watchdog) and links
step 0 and the key's reference row. When #610 restructures Getting
Started, the link moves with the step.

**D4. Other local runners are one table and one rule.** What changes
per runner is `base_url` and the model-id vocabulary, which the issue
says is the point worth making once: a short table (Ollama
`http://host.docker.internal:11434/v1` and `ollama list` names;
llama.cpp's `llama-server` `:8080/v1` and the loaded GGUF's alias; LM
Studio `:1234/v1` and its model key; vLLM `:8000/v1` and the Hugging
Face id), each runner's default port taken from its own documentation
at the time of writing and cited, and one recipe written in full.

**D5. Vendors.** Anthropic is its own type and knows its own reach
(`reach` is refused on it). OpenAI is `openai_compatible` with
`base_url` left at its default, a credential, `reach: internet` under a
declared boundary, and the `max_completion_tokens` passthrough the
example names for current OpenAI models. The compatible vendors (Groq,
OpenRouter, Together) are the same entry with their `base_url`; the
guide names their endpoints from their documentation and says they were
not run (no keys).

**D6. Credentials.** The two paths from the issue, written the way #609
settled: `api_key_env` naming a variable the server's environment
carries (put in the deployment's env file without the shell expanding
it, the 0600-file pipe form `docs/run/security.md` documents, linked
rather than restated), or `vinga provider secret set llm <name>
api_key`, which reads stdin and takes precedence over the reference for
the same slot. Never a `key=value` argument; the CLI's own refusal is
the backstop, and the guide says so.

**D7. Verification is execution, recipe by recipe, and the record says
which ran.** The implementer runs each recipe against a vinga-server
started from the worktree (Postgres from the compose service), writing
the provider with the guide's exact commands, applying, and then:

- the **Ollama recipe** by the local lane (`VINGA_LOCAL_LANE=1 uv run
  pytest tests/local -q`, with `VINGA_LOCAL_LLM_MODEL=llama3.1:8b` and
  Ollama in a container, `ollama/ollama`, since agentpi has none
  installed), which holds a real spoken conversation and a real tool
  call through it. If the Pi's CPU cannot answer inside the watchdog
  even warm, the implementer raises `llm_first_token_timeout_s` for the
  run and records the measured first-token times, which is itself a
  fact the guide's criteria should be checked against;
- the **llama.cpp recipe**, the **Anthropic recipe** (with
  `VINGA_DEV_ANTHROPIC_API_KEY` exported as the variable the recipe
  names) and the **OpenAI recipe** (with `VINGA_DEV_OPENAI_API_KEY`) by
  one conversation turn through the device simulator against a server
  whose ASR and TTS are the `mock` type and whose LLM is the recipe's
  entry, so the turn exercises exactly what the recipe wrote: the write,
  the apply, and a real reply from that endpoint. The harness is a
  throwaway script under `.logs/` (not committed), adapted from the
  smoke lane's simulator use; its output (the reply text's length, the
  `llm_round` event's timings, never a credential) is quoted in the
  record;
- **LM Studio, vLLM and the compatible vendors** are not run (a desktop
  app, a GPU server, no keys), and the guide and the record say exactly
  that.

## Risks

- **A recipe that was not run reads as if it was.** D7's record is per
  recipe, and the guide marks the unrun ones in its own words.
- **Credentials in documented commands.** #609's lessons apply: no
  secret in an argument, an expanded assignment, or a `printf` the shell
  traces; the curl config file or the 0600 env-file pipe. The D8a grep
  from #609's plan runs over the new page.
- **A claim about the server that the code contradicts.** #609 found
  dozens in the README. Every claim the guide makes about what the
  server refuses, retries, coerces or logs is checked against `src/`,
  and the record lists them with file and line.
- **The preset change breaks a test that pins the preset's model.** The
  untruncated grep above found none; the unit lane runs because an
  example changes.
- **Running an 8B model on the Pi.** Pulling `llama3.1:8b` is about
  5 GB and CPU inference is slow; the implementer records the measured
  timings rather than assuming them, and a timeout raised for the run is
  stated, never hidden.

## Standing lenses

No-leak: no credential in any command, log or record (the harness
prints lengths and timings only). Pin before reshaping: not applicable,
nothing moves. Closed sets and honest seams: none added. Inventories by
tooling: the `qwen3` and credential greps are untruncated and kept in
`.logs/`. Proportion: the "Cheapest alternative" line. Falsify before
claiming: each recipe is executed, and a recipe whose execution fails
is fixed or marked, never claimed.

## Plan review round

Reviewed 2026-10-06 by openai/gpt-6-sol, thinking high via codex CLI 0.160.0, read-only sandbox, runtime 3m30s, at commit d1b9c9d4, plan blob 27ec5fb0.

---

1. **P1: The plan changes the issue's settled default.** Evidence: issue #364 specifies Ollama with `qwen3:8b`; D1 (`docs/plans/2026-10-06-llm-guide.md:92`) replaces it with `llama3.1:8b` and changes the preset. The plan should keep `qwen3:8b` as the default and reconcile Getting Started with that decision. A different default needs an amendment to the issue, not a smaller plan decision.

   *Resolution:* Accepted. D1 no longer changes the default: the guide leads with the issue's `qwen3:8b`, states that Getting Started installs `llama3.1:8b` and why, and gives both against D2's criteria with the dated measurements. The preset, the example and the security snippet are untouched. The single-default question goes to Rafael on #364 and in the PR; either answer is a one-line change in three files.

2. **P1: The OpenAI recipe would be refused at write time.** Evidence: D5 (`docs/plans/2026-10-06-llm-guide.md:133`) leaves `base_url` at a presumed default, but the generated provider reference (`docs/reference/domain-config.md:186`) and the options model (`vinga-server/src/vinga_server/config/provider_options.py:1037`) require it. The plan should specify `base_url=https://api.openai.com/v1` in the worked recipe.

3. **P2: Agent selection needs a rule that preserves the existing entry.** Evidence: the plan requires an `agent set` or `agent-defaults set` line for each recipe but does not say how to retain other fields (decisions (`docs/plans/2026-10-06-llm-guide.md:72`), M1 (`docs/plans/2026-10-06-llm-guide.md:238`)). Both commands **replace the whole entity** (domain reference (`docs/reference/domain-config.md:59`)); a bare `llm=<name>` can discard stages, prompts or tool grants. The plan should require exporting and editing the selected entity, then setting its complete body and applying it.

4. **P2: The local test does not execute the Ollama recipe.** Evidence: D7 (`docs/plans/2026-10-06-llm-guide.md:151`) claims exact guide commands will be exercised by `tests/local`, but the tool test (`vinga-server/tests/local/test_tool_calling_for_real.py:90`) constructs its own `Config` and server. The plan also attributes preset composition to `test_config_examples`; the preset integration test (`vinga-server/tests/integration/test_cli_live.py:2770`) imports presets but deliberately does not apply them. The plan should run the Ollama guide commands against a running deployment and verify that the selected agent answers through that entry. Keep the local lane as an additional tool-calling check.

5. **P2: The vendor and llama.cpp checks cannot establish tool capability.** Evidence: D2 (`docs/plans/2026-10-06-llm-guide.md:108`) makes real tool calls a selection requirement, while D7 (`docs/plans/2026-10-06-llm-guide.md:164`) checks only an ordinary reply for those endpoints. The plan should exercise a tool call for each run recipe, or label tool calling unverified for that recipe.

6. **P2: `host.docker.internal` alone does not make a host runner reachable on Linux.** Evidence: D4 (`docs/plans/2026-10-06-llm-guide.md:124`) reduces runner differences to URL and model ID, while Getting Started (`README.md:190`) documents that Linux Ollama also needs a listener reachable from the container. The plan should make host-interface binding and container reachability explicit prerequisites for local-runner recipes.

7. **P2: The credential paths omit prerequisites for a running deployment.** Evidence: D6 (`docs/plans/2026-10-06-llm-guide.md:142`) points to a 0600 pipe in the security guide (`docs/run/security.md:60`), but that procedure generates new secrets; it does not safely enter an existing vendor key. The database path requires `VINGA_MASTER_KEY` (secret store (`vinga-server/src/vinga_server/config/secrets.py:232`)). The plan should specify a protected editor-written env file for an existing key and a server restart to load it, or the stored-secret path after configuring and retaining the master key. Neither path should expand the credential in a shell command.

8. **P2: Switching a local deployment to a vendor may require a server restart.** Evidence: D5 (`docs/plans/2026-10-06-llm-guide.md:133`) prescribes `reach: internet`, but a deployment with `server.data_boundary: host` refuses that provider (server reference (`docs/reference/server-config.md:111`)). The boundary is server configuration, read at startup (domain reference (`docs/reference/domain-config.md:63`)). The plan should tell readers to inspect the boundary and, if they choose vendor egress, change it deliberately and restart before applying the provider.

**Verdict:** Ready after the P1/P2 amendments.
